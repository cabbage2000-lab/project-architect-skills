# 必要文档检查判据

## 取证

在完成[规模判断](project-size.md)后，按本轮选定的范围取证。列出根目录的说明、贡献指南、项目手册、相关子模块文档及项目认可的文档入口。按下表的类别定位资料，沿正文中的相对路径、章节链接和外部引用读到实际回答问题的段落。同一份 README 或手册可以覆盖多个类别。列举文件和阅读正文分别记录。

### 确认适用性

以本轮交接任务和项目实际交付方式为准。小型服务可能需要部署和 API 说明，大型本地工具也可能只需要本地使用和验证说明。

- 主要流程与业务规则从需求说明、用户手册、可重放的示例和验收用例核实。小工具可在一段说明中交代输入、输出及关键约束。业务意图或例外规则存在冲突时，记录出处和待核实点。
- 架构说明从维护入口、目录职责、工作区清单及实际依赖核实。有多个协作模块、外部依赖或关键数据流时，检查维护者能否据此定位改动和受影响的部分。单入口脚本可用简短说明满足需要。若没有需要交接的模块边界或依赖，给出入口和结构依据后可判为「不适用」。
- 必要配置从入口、配置声明和样例核实。先找阻止正常启动或调用的必填项，再查文档是否说清位置和获取方式。
- 部署从交付声明、发布流程或服务运行入口核实。Dockerfile 和 CI 文件可作为查找线索，继续确认它们服务于本地开发、测试还是实际交付。
- API 从面向使用者公开的路由、库导出、协议或扩展入口核实。检查任务涉及的实际调用方式，包括非 HTTP 接口。

### AI 编程工具项目指引

从维护者的明确说明、贡献指南中的开发步骤、仓库启用的工具配置或 CI 调用核实工具用途。仅在示例中提到工具、机器上装有 CLI，或本次借它体检另一个项目，都不足以证明目标项目用它开发。已查开发流程没有使用迹象时，记录检索范围并标为「不适用」。有使用线索但用途或检查范围无法核实时标为「待确认」。

按实际工作目录逐个核对入口。项目已约定具体文件名时核对该路径，读取正文和引用目标，确认接手者能取得适用的仓库约定。目录清单应包含隐藏目录，并保留文件名的实际大小写。

- **Claude Code** 核对 `CLAUDE.md`、`.claude/CLAUDE.md` 及对该目录生效的项目规则。若已证实当前版本和配置能直接加载共享的 `AGENTS.md`，或 `CLAUDE.md` 通过 `@AGENTS.md` 引用它，记录共享入口及依据。[Claude Code 项目指引](https://code.claude.com/docs/en/memory)
- **Codex** 从项目根到工作目录逐级核对 `AGENTS.md`，同时检查优先加载的 `AGENTS.override.md` 或项目已配置的后备文件名。子模块的专用指引只覆盖其生效范围。[Codex 项目指引](https://developers.openai.com/codex/guides/agents-md/)
- **其他已采用的工具** 按已核实的项目配置或该工具支持的入口检查。个人主目录中的指引不能作为团队可交接的项目入口。

工具已用于项目且已查全适用位置，仍缺少入口时，报「发现问题」并填 `missing`。在 `evidence` 引用使用依据和实际目录检索结果，在 `placement` 填应补建的文件路径。已有入口只有空模板时填 `incomplete`。可加载的入口给出项目约定或引用仓库手册时，记为「范围内未发现」。若使用替代文件，写明缺少的常规文件名及实际生效的路径。

### 核对正文和引用

1. 用现有文档入口、链接和同义标题定位答案。文件名和标题可用于定位。若相关章节只有模板提示、注释、空表格、占位符或与本项目无关的示例，继续查找可用正文。
2. 对照入口、构建清单、命令注册、测试或 CI 核实文档的关键断言。对命令核对工作目录、参数和输入来源，对样例核对所需字段和预期结果，对链接核对目标文件或章节。手册指向可用的帮助页、配置样例或 CI 操作指南时，把引用和目标一起作为证据。只有实现中能找到答案时，用它作为补写依据。
3. 记录被卡住的具体动作和对照过的出处。比如手册写了测试命令却未提供它所需的输入时，引用该命令和脚本入口，写清要补哪份样例。上轮体检报告用于回溯。架构图可作为架构说明的证据。图本身的缺失或失效交给[架构图检查](architecture-diagrams.md)，架构文档只记录独立的交接说明缺口。

引用已有内容时给出相对路径及行号或章节。缺失项写明实际检索的目录、文档入口及已读资料覆盖到哪里。即使项目没有手册，检索范围也能作为依据。对外部资料引用已打开的 URL 和段落。引用无法打开时记录原文位置、目标和原因。只读到子目录时记录子目录，以及缺少的上层资料。将未读资料关联到它可能回答的检查项。例如测试手册影响验证项，唯一的模块说明链接影响架构项。

### 文档冗余

完整文档检查包含 `redundancy`，也可单独派发。按读者要完成的任务，在同一文档的不同章节和不同文档之间对照操作步骤、配置表、业务规则及整份手册。相同的命令、字段或近义标题可帮助定位候选，逐段核实它们面向的版本、读者和使用场景。用不同措辞维护同一套规则也可能冗余。

确认两处或更多正文独立维护同一内容，且一次变更需要多处同步或读者难以判断以哪处为准时，记录为「发现问题」。写明重叠段落及具体影响，依据项目指定的入口、内容归属和读者可访问性选择保留正文的位置。核对其他入口的引用及独有步骤，说明如何用链接替代重复部分、保留各自的上下文。

快速入门中的摘要和链接、面向其他版本或读者的专用步骤、历史快照和由同一来源生成的副本，都可能有独立用途。核实用途后可记为「范围内未发现」。另一份正文读不到，或版本、用途差异仍可能改变判断时，将该组标为「待确认」，写明所缺依据。其他已核实的重复组仍可独立给出合并建议。

## 按文档类别核对

| 类别 | 标识 | 核对的问题 | 可以采信的答案 |
| --- | --- | --- | --- |
| 产品文档 | `purpose` | 这个项目帮谁完成什么任务？ | 说明一次真实用途或输入输出，读者能判断是否找对项目。 |
| 产品文档 | `requirements` | 主要使用流程是什么？哪些规则影响本次维护？ | 说明关键步骤、规则或约束，以及相应的预期结果。需求文档、用户手册或带预期的业务样例均可提供依据。 |
| 技术文档 | `usage` | 怎样第一次走通主要入口？ | 可执行的启动步骤，或库、CLI、Skill 等的最小使用示例。按该项目实际需要核对前置条件和工作目录。 |
| 技术文档 | `configuration` | 走通这条路径必须先准备什么配置？ | 必填项、设置位置及可用的样例或获取方式。入口使用内置默认值且无必填配置时，可据入口或配置声明判为「不适用」。 |
| 技术文档 | `api` | 是否有使用者需要调用的接口？若有，怎样完成一次典型调用？ | 可定位的接口、输入、输出或可访问的契约与调用示例。同一个可运行的库示例可以同时覆盖最小使用和 API。内部函数的存在本身不足以要求 API 手册。 |
| 技术文档 | `agent_instructions` | 开发中使用的每种 AI 编程工具能从哪里读取本项目的约定？ | 工具使用依据、已核对的生效范围，以及可读取的项目指引或缺失的入口。 |
| 架构文档 | `architecture` | 从哪里找到主要职责、依赖方向和改动影响？ | 描述本轮涉及的模块边界、调用或数据流，并能对照当前入口和实现。现有手册中的文字、结构图或其可访问引用均可提供依据。 |
| 测试文档 | `verification` | 改完后，怎样知道仍然正确？ | 适用的测试命令与成功信号，或可重放的手工样例和预期结果。一次启动能验证该任务时，说明观察什么即可。 |
| 部署文档 | `deployment` | 项目用途或交接任务是否涉及部署？若涉及，如何完成并确认可用？ | 项目声明支持的部署路径、必要条件和成功信号。本地工具或库可以依据其交付方式判为「不适用」。 |

## 判断与补写位置

对上表的交接主题按以下状态给出结论。

- **范围内未发现**表示该问题在已读资料中有可用答案。写下答案和出处，包括分散在不同资料中的步骤。
- **发现问题**用于相关资料已核对、仍缺少交接答案的情形。写清已有资料覆盖到哪里、具体卡住的动作和补写位置。一般说明优先补入现有手册，没有手册时建议新建最小入口。工具需要特定文件才能读取指引时，建议在其生效位置补建入口并引用已有说明。
- **待确认**写清缺哪份资料、哪项用途待核实或哪两处依据冲突且尚无法核实实际行为。项目级资料未查全时，已证实的覆盖仍然有效，受限制的缺失判断保留为待确认。完整性与已证实的独立缺口可同时呈现。
- **不适用**须给出项目用途、分发方式或实际实现的依据。没有搜到部署、配置或 API 说明，本身不足以判定其不适用。

已确认的「发现问题」按本轮受阻步骤记录最贴切的缺口类型。

| 标识 | 类型 | 判断依据 |
| --- | --- | --- |
| `missing` | 缺少说明 | 已核对相关入口，现有文档没有回答这个交接问题。 |
| `incomplete` | 内容不完整 | 有对应章节或链接，正文仍是骨架，或缺少走通所需的输入、步骤或成功信号。 |
| `stale` | 与实现不符 | 已核实当前实现，文档指向失效的链接、命令、参数或行为。 |

引用因权限、网络或范围限制无法核实时，记录受影响的检查项。已有证据不足以确认该项结论时，将其标为「待确认」。报告按文档类别列出逐项结论及依据，并在「建议补写」中按相同类别列出已确认的缺口和补写位置。

同一检查项仍有未读资料时，已用独立证据确认的 `stale` 保留为「发现问题」，报告的资料完整性标为「待确认」。例如，已验证 README 的旧命令失效，即可提出修正建议，同时记录无法打开的验收手册。需要通过未读资料才能确定是否缺少说明或内容的记录仍为「待确认」。

## 交给汇总脚本的记录

用 `python3 -B <本 Skill 目录>/scripts/necessary_docs.py` 传入 UTF-8 JSON。也可以在命令末尾传入记录文件路径。宿主负责阅读和判断，脚本负责完整性、候选筛选和报告格式。只读检查可以直接通过标准输入完成。

只问某个主题时，把派发项放进顶层 `selected`，如 `[{"check":"redundancy","unit":"订单导出"}]`，在 `topics` 填对应主题及证据。加 `--json` 取得章节和[专项覆盖记录](governance-plan.md#检查范围记录)。省略 `selected` 时按完整文档检查处理。

- `project` 记录检查前的规模依据。`units` 和 `files` 分别是独立维护单元数和自维护文件数，取非负整数，未知可填 `null` 或省略对应字段。`evidence` 是非空字符串数组，记录计数来源与口径。`focus` 是非空字符串，说明本轮按规模和维护任务选定的入口、模块或流程。汇总脚本按计数重算规模。旧记录可以省略整个 `project`。
- `scope` 是已查位置的字符串数组，写明实际检索、阅读的路径或范围。
- `unread` 是未查全的相关资料数组，均已核实时传入 `[]`。每项含 `source` 和 `reason`。用可选的 `topics` 数组列出受影响的标识，省略时表示可能影响全部检查项。
- 上表交接主题的记录各含 `status`（上面的中文状态）、`detail`（已覆盖的答案、具体缺口或状态原因）和 `evidence`（出处数组）。拟报「发现问题」的项另含 `gap_kind`（缺口类型）、`impact`（会卡住哪一步）和 `placement`（建议补写或修正的位置及内容）。旧记录可以省略 `gap_kind`。
- `topics.agent_instructions` 为非空数组，每种工具一条上述记录，用 `tool` 写工具名。没有适用工具或工具尚不明确时，填一条带依据的「不适用」或「待确认」记录，可省略 `tool`。仅影响某个工具的未读资料填在该条目的 `unread`，每项含 `source` 和 `reason`。专项点名工具时，用 `agent_instructions` 作 `check`，以每种工具和工作目录作 `unit` 分别回传。
- `topics.redundancy` 为非空数组，每组对照单独填 `status`、`detail` 和 `evidence`。已确认冗余时，`evidence` 至少列两处不同的正文位置（路径加行号或章节），第一处为建议保留的正文，其余为重复位置。`detail` 说明重复的内容和保留依据，`impact` 写明维护影响，`placement` 说明其余入口如何调整。没有发现时提交一条说明已比对范围和依据的记录。

旧版六项、八项和九项完整记录仍可汇总，缺少的新主题显示「待确认」。

## 最小可运行示例

这个[完整检查记录](examples/necessary-docs-record.json)使用虚构的订单导出工具演示输入格式。维护本 Skill 时，在 `project-architect-skills` 仓库根目录运行以下命令。

```sh
python3 -B skills/project-architect-skills/scripts/necessary_docs.py \
  skills/project-architect-skills/references/examples/necessary-docs-record.json
```

标准输出以 `## 必要文档` 开头。「建议补写」列出 Codex 缺少的 `AGENTS.md`、模块职责和测试成功信号。Claude Code 已通过 `.claude/CLAUDE.md` 取得导出规则。「文档冗余」列出两份导出规则的位置、建议保留的正文和操作手册中应保留的示例。宿主按维护影响将候选纳入治理计划。合并获批后，应从各原有入口核对链接、独有步骤和共享规则。
