# 架构图检查判据

## 补架构图

先按[项目规模](project-size.md)确认维护单元，从用户指定的模块或项目主要入口选择新人要理解的业务路径。沿入口查代码、配置和已有图，优先复用能回答问题的视图。可按以下线索选择图型。

| 规模 | 新人需要弄清的关系 | 可推荐的视图 |
| --- | --- | --- |
| 小项目 | 一次操作从哪里开始，经过哪些模块或外部依赖？ | 有跨模块调用时画简短的入口调用图。单脚本且流程直观时，可直接说明现有使用示例已足够。 |
| 中等项目 | 各模块怎么分工，一次关键操作怎样跨越模块边界？ | 先考虑模块依赖图。需要判断调用先后或数据流向时，补业务时序图或数据流图。 |
| 大项目 | 系统与外部服务的边界在哪里，接手者负责哪一段？ | 先考虑系统上下文图或服务关系总图，再针对所选链路展开。需要理解运行环境且有部署清单时可补部署图。 |
| 规模待确认 | 当前可见的入口能追到哪里？ | 推荐有证据支撑的局部视图，标明覆盖边界。 |

只问推荐时，在会话逐项给出优先级、图名、能回答的问题、已有图的覆盖情况和建议位置。泛问「帮我补架构图」时，让用户从推荐中选全部、部分或另行指定。用户已点名图型、业务范围或目标文件，或已委托按推荐直接补齐时，主 Agent 直接新建或更新相应图件。

按用户指定的格式与位置交付，其余沿用项目惯例。项目没有约定时，可把可编辑的 Mermaid 图放入相应架构说明。写清节点职责，给关键连线标明调用、事件或数据的方向。证据不足的部分在交付说明中列为待确认。

先编辑源图，再同步项目实际引用的导出图。保密图的源文件、预览和引用均留在认可的私有范围。项目用 Git 忽略规则保护图件时，分别核实源图与导出路径。交付时给出图件位置、关键关系对应的源码或配置，核对渲染结果、箭头方向与引用。未能验证的步骤如实说明。

## 查找并对照实现

1. 按[项目规模与取证范围](project-size.md)确定本轮模块和入口。先从工作区清单、实际入口和调用位置核对是否有需要交接的模块、外部依赖或数据流。一个入口直接完成任务且无相关模块边界时可判为「不适用」，并记录依据。仅凭没有找到图无法判断适用性。
2. 盘点仓库根、README、项目手册、相关模块文档和图件目录，顺着项目认可的引用打开图。包括 Markdown 内嵌 Mermaid、`.drawio`、SVG 或位图以及外部链接。记录实际检索的位置和已读图的路径、页名或章节。产品功能图可用于核对目标流程，交接当前实现时还需找到模块关系视图。用同一内容的源图和导出图互证，合为一份实现视图记录。
3. 从图中读出本轮相关模块及连线。逐条用实际入口、调用、导入、路由、配置或测试核对节点和方向，记录具体证据。按图中声明的层级和含义核对，保留合理省略。多张实现视图可以互补，合并检查其覆盖后再判断关键关系是否漏画。比较节点改名、依赖方向变化或关键关系缺失时，写清图中原意与代码的实际行为。还需核对加载器、框架注册或消息中转的关系时，先追踪对应入口。
4. 找不到实现视图时，检查当前范围是否查全。只看到了子目录、读不到图件内容或访问不了可能改变结论的引用时，记录出处、目标和受限原因。已从代码确认的过时连线可独立报告。对仓库内失效的图件引用，先查找是否迁移，再记录能确定的错误路径及应指向的位置。

## 状态与修订

图件存放位置遵循[保密文档规则](necessary-documents.md#保密文档)。若缺图判断只源于约定路径在工作区缺席，将原路径填入 `need.expected_path` 并在目标仓库根运行脚本。Git 确认忽略后，报告保留业务上需要图件的理由，将该路径的仓库交付检查列为「不适用」。已读图中可核实的错误仍独立评估。

| 状态 | 判断依据 |
| --- | --- |
| 范围内未发现 | 已核对本轮交接所需的模块关系，图与实现一致。单独记录仍未读到的资料。 |
| 发现问题 | 可确认图中标注与当前实现不符、关键关系漏画，或查全后确定无实现视图。仅有产品功能图时指出缺少的实现关系。一个检查范围汇总为一个候选，保留每条证据。 |
| 待确认 | 适用性、关键关系或图件覆盖仍可能受未知资料影响。列出还需要读到的资料。 |
| 不适用 | 有入口和职责证据，当前交接无需图说明模块关系，或约定的图件路径受 Git 忽略规则保护，免查仓库交付情况。 |

与[必要文档检查](necessary-documents.md)一起运行时，图可作为文字架构说明的证据。图的缺失或差异归在「架构图」，文字本身的职责与依赖说明缺口归在「架构文档」。同一图件问题只进入一次治理计划。

体检发现的缺图或错图获准修订后，按[补架构图](#补架构图)更新源图和引用，并用本轮对照过的代码复核。

## 交给汇总脚本的记录

用 `python3 -B <本 Skill 目录>/scripts/architecture_diagrams.py` 从标准输入读取 UTF-8 JSON。也可在命令末尾传入记录文件。宿主负责读取和判断，脚本输出一段「架构图」Markdown。单独检查时传入与必要文档检查相同格式的 `project` 规模依据。与必要文档合并且前面已列规模时，可省略 `project`。

- `scope` 是非空字符串数组，写实际检索的位置和交接范围。`need` 含 `status`（`需要`、`不适用` 或 `待确认`）、`detail`（理由）和非空字符串数组 `evidence`（出处）。
- `unread` 列可能影响本轮的未读资料，每项含 `source` 和 `reason`。本地文件的 `source` 用仓库相对路径。与已核实保密的 `need.expected_path` 相同的来源免计，其余未读资料仍按范围记录。没有时传入 `[]`。
- `diagrams` 每项含 `source` 和 `kind`。`product` 项提供 `detail` 说明其层级。`implementation` 项提供非空 `checks`，每条含 `claim`（节点、连线或引用）、`result`（`一致`、`与实现不符`、`缺少关键关系` 或 `待确认`）、`detail`（真实关系及其与图的差异）和非空字符串数组 `evidence`。把已确认的本地失效引用作为 `与实现不符` 记录。未看到任何图时传入 `[]`。
- 确认为缺口时提供一个 `repair`，含 `impact`（受阻事项）、`placement`（修订位置）和非空字符串数组 `changes`（需增加或修正的模块关系及源码出处）。脚本在同一范围输出一份建议修订。仅有产品图、缺图或关系未查全且有未读资料时，先给出待确认结论。

### 最小示例

在本仓库根目录运行以下命令，用虚构项目演示仅有产品图的报告。

```sh
python3 -B skills/project-architect-skills/scripts/architecture_diagrams.py <<'JSON'
{
  "scope": ["通查 README、docs/ 和 src/ 的订单导出入口"],
  "need": {"status": "需要", "detail": "维护导出要定位入口和订单读取。", "evidence": ["src/export.py:8"]},
  "unread": [],
  "diagrams": [
    {"source": "docs/flow.drawio#导出流程", "kind": "product", "detail": "图中只有选择订单和下载两个操作。"}
  ],
  "repair": {
    "impact": "接手者无法判断哪些代码读取订单。",
    "placement": "在 README 的架构说明补入实现视图。",
    "changes": ["画出 export → orders，依据 src/export.py:8。"]
  }
}
JSON
```

标准输出以 `## 架构图` 开头，报告仅有产品功能图、缺少实现视图，并给出一条修订建议。
