# 治理计划

## 从体检发现确定本轮改动

1. 汇集本轮所选检查的发现及维护影响，引用仓库相对路径、符号或章节。同一改动能解决的多个发现合为一项，并保留各自的证据。例如同一方法的多类异味、多个章节提到的同一图件缺口。需要一起修改和回退的文件归入同一事项，写清改动范围。
2. 按当前维护任务的具体阻碍排列候选。没有指定任务时，优先处理直接妨碍启动、定位入口或验证改动的问题。优先选择证据充分、能独立验收和回退的事项。维护影响相近时，可用 [Git 变更热点](git-change-history.md)辅助排序。综合这些依据，选出最值得本轮优化的事项，数量由评估结果决定。逐项说明优先理由并引用可复核的依据。
3. 给拟执行的事项记录最小改动范围、执行步骤和改前实测基线。先核对目标文件的当前内容及已有编辑，以原有入口、测试、固定输入或源码对照建立可重放的基线。验收写明操作、预期变化和需核对的行为。代码改动同时核对结构目标、主要调用方和用户可见行为。文档按说明实际操作，图件核对节点、连线和对应源码。回退写明恢复哪些位置、以哪个改前状态为准，以及怎样确认回退成功。
4. 业务规则或适用性仍需核实的事项记为「待确认」。缺少关键基线或验收条件时记为「待验证」。其他因本轮优先级、权限或回退条件暂时无法安排的事项记为「暂缓」。记录具体原因，继续处理相互独立的事项。授权前以只读方式取证。基线操作会写入时，可在仓库外的隔离副本运行，并核对结果是否适用于当前工作区。

展示拟修复的目标仓库、具体范围和验收方式后，在当前会话等待用户回复「同意治理」或其他明确批准。已有明确授权的具体修复沿用原授权。工作区可写只表示具备写入能力。获批后沿用原计划顺序，开始每项前重新核对证据、基线和工作区状态。已解决的事项跳过。证据、编辑或验收条件变化时，记录跳过或暂缓的原因。新增或扩大改动范围须先获得确认。保留原计划和实际复核记录，用计划项的序号和标题关联两者。

### 代码重构的行为基线

从本次改动容易破坏的调用约定选择样例。例如把循环里的嵌套条件改为提前跳过时，用一组「首条应跳过、第二条应保留」的数据运行原入口，记下输出及顺序。这个样例能区分跳过当前记录和提前结束整个函数。若现有测试已覆盖该路径，直接复用。缺少覆盖时可在隔离副本中用固定输入记录当前行为，或运行刻画测试（以原实现的实际行为作为断言）。需要把测试纳入目标仓库时，将测试文件一并列入拟改范围。

在 `steps` 中把手法与发现对应起来，例如提取两处调用方共有的计价规则，或拆开能独立验证的处理阶段。在 `acceptance` 中分别写明如何重放行为样例、如何判断维护负担减轻，例如下一次改计价规则需要编辑几处。遇到公共符号改名，先核实外部调用约定和兼容入口；确实需要调用者迁移时，将迁移范围单独说明并取得授权。

### 设计模式的选择与验收

按实际维护任务比较最小改法和拟用模式，在计划中写明哪处变化能被集中、调用方要多经过哪些间接调用，以及选择理由。一个函数或查找表已能集中规则时，优先采用该方案。

例如报价和结算都按运输方式选择计费算法，新增运输方式时曾出现一处漏改。可先提取共享计费函数；当各算法确实独立演进且两个入口都需要替换算法时，可在共享入口按运输方式注册计费策略。结构验收核对接入一种策略需要修改的位置；行为验收从报价和结算分别重放已有费率、舍入边界及未知运输方式的样例。若变化来自供应商 SDK 的参数或错误类型，可考虑在集成边界用适配器转换，并通过业务入口验证错误映射。

## 生成报告章节

用 `python3 -B <本 Skill 目录>/scripts/governance_plan.py` 从标准输入读取 UTF-8 JSON，或传入记录文件。宿主将本轮推荐且具备执行条件的事项标为「可执行」。脚本按提交顺序列出全部「可执行」事项，并在同一章节保留其余发现及未纳入的原因。等待授权时加 `--preview`，有入选事项才输出回复「同意治理」的提示。获批后复用同一计划记录汇总正式报告，将计划放在体检与执行复核之间。

- `mode` 为 `execute`（拟定或汇总治理计划）或 `inspect`（只交付检查与建议）。`execute` 选择可执行事项，写入由宿主根据当前会话的授权决定。`inspect` 的候选均显示「未执行」，适用于只读、用户拒绝或仓库不可写的情况。
- `candidates` 按优先级排列，无候选时传 `[]`。每项含 `target`（合并后的唯一治理目标，可用路径及符号或章节表达）、`title`、非空 `evidence` 出处数组、`impact`、`status` 和 `reason`。`reason` 对执行项给出优先理由，对其余项说明受阻或暂缓原因。仅检查的候选可用 `status: "未执行"`，并说明该建议对应的检查目的或已知限制。
- `execute` 模式中，「可执行」事项还需 `scope`、`baseline`、`steps`、`acceptance` 和 `rollback` 五段非空文本。其余事项使用「待确认」「待验证」或「暂缓」。

### 最小示例

在本仓库根目录运行以下命令，样例中只纳入补写测试说明的事项。

```sh
python3 -B skills/project-architect-skills/scripts/governance_plan.py --preview <<'JSON'
{
  "mode": "execute",
  "candidates": [
    {
      "target": "README.md#验证", "title": "补写最小验证步骤",
      "evidence": ["README.md#运行", "tests/test_names.py:6"],
      "impact": "接手者能运行项目，但缺少检查姓名排序的步骤。",
      "status": "可执行", "reason": "验证步骤直接服务于本轮交接。",
      "scope": "在 README.md 的运行章节补写测试命令和预期结果。",
      "baseline": "已读取运行章节并执行 `python3 -B -m unittest discover -s tests`，1 项通过。",
      "steps": "追加验证小节并记录实际通过的命令。",
      "acceptance": "按新小节运行命令，退出码为 0 且显示 1 项通过。",
      "rollback": "删去新增小节，与改前保存的 README.md 对照后重跑命令。"
    },
    {
      "target": "src/names.py::sort_names", "title": "核实同名输入的排序规则",
      "evidence": ["src/names.py:12", "src/import_names.py:18"],
      "impact": "合并相似的排序逻辑可能改变同名记录的次序。",
      "status": "待确认", "reason": "批量导入是否需要保留原始次序尚无业务依据。"
    }
  ]
}
JSON
```
