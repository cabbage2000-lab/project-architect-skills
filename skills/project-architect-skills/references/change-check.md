# 本次改动体检

## 确定比较范围

从目标 Git 仓库根目录运行 [change_check.py](../scripts/change_check.py)。默认检查暂存区、未暂存改动和未被忽略的新文件。指定提交时使用本地引用，两个点比较端点，三个点从两端的共同祖先比较到右端。

```sh
python3 -B <Skill目录>/scripts/change_check.py
python3 -B <Skill目录>/scripts/change_check.py --range 'HEAD~1..HEAD'
python3 -B <Skill目录>/scripts/change_check.py --range 'main...feature'
```

JSON 的 `changes` 是取证清单。成功且为空时，报告比较范围和「范围内没有改动」，到此结束。Git 不可用、引用不存在或对象不可读时说明缺哪个范围。用户已提供补丁时可按可见差异继续，注明上下文限制。Python 不可用时，在 `GIT_OPTIONAL_LOCKS=0` 下用 Git 盘点。提交范围先用 `git rev-parse --verify` 确认两端，三个点另用 `git merge-base --all` 确认唯一的共同祖先，再用 `git diff --name-status -M` 比较实际端点。

| 范围 | 从哪一版取证 |
| --- | --- |
| 未提交改动 | 用 `git --no-optional-locks status --porcelain=v2 --untracked-files=all` 盘点。清单的两位状态分别表示暂存区和工作区，点表示该层未改。`git diff --cached` 看暂存版本，`git diff` 看工作区相对暂存区的变化。用 `git show ':路径'` 查暂存内容，用 `git grep --cached` 查该版引用。同一路径两层均改，或调用方修复仅存在于工作区时，说明单独提交暂存内容的结果。尚无首个提交时，已暂存文件按新增处理。 |
| 提交范围 | 清单给出解析后的 `base` 和 `target`。用 `git diff <base> <target> -- <路径>` 读差异，用 `git grep -n -e <符号> <target> --` 和 `git show '<target>:路径'` 读同版调用方、文档和测试。删除或重命名时也查旧路径、旧符号和基线版本。当前工作区可能已包含后续修复。 |

`??` 路径按新增内容核查。涉及私有手册或图件时，沿用项目的[保密文档约定](necessary-documents.md#保密文档)。遇到冲突、子模块版本变化或无法读取的二进制资料，写明可核实的部分和仍需取得的证据。

## 顺着一次行为变化核对

1. 从差异中找出使用者能观察到的变化。写清触发条件和改前、改后的结果。例如列名改变时，找到哪条记录会导出新表头。单纯移动或内部整理可记录为「在已查入口未发现行为变化」，并给出判断依据。
2. 从改变的符号、字段、命令或路径反查实际消费者。打开调用点、配置、公开说明或图件，判断哪处已经同步、哪处仍依赖旧行为。调用方和文档即使没有出现在差异里，也可能是主要发现。历史共变只作为查找线索。
3. 按[行为验证判据](behavior-verification.md#沿同一条路径取证)核对本次变化涉及的路径及适用样例。打开相关测试，核对输入是否触发本次变化、断言是否能区分改前改后。对每个重要缺口给出能重放的最小输入、操作和预期结果。区分「已有用例但未运行」「缺少对应断言」和「已实跑」，写明实跑的版本及观察。验证会写文件时在仓库外的相应版本副本运行。

在会话中先写比较范围及实际已查范围，再按维护影响列出发现。每条把**变化、受影响的位置、验证缺口或实测结果**连在一起，引用差异位置和相关调用方、文档或用例的位置。没有发现遗漏时简述抽查过的行为和证据，资料不全时写清哪些结论仍待确认。体检保持只读。用户另行要求修复时，从已证实的发现进入现有治理计划。
