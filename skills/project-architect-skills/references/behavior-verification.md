# 行为验证判据

一份记录跟踪一个真实入口。检查跨入口规则时，按同一业务规则给相关入口分组，一组一份记录。全面质检优先验证用户要维护的功能，其次选快速开始展示的主要用途。若没有快速开始，从实际交付的命令、库导出或服务入口选择一条代表性路径，写明理由。只有资料、没有可执行行为的项目可按实际交付内容说明「不适用」。

## 沿同一条路径取证

| 检查项 | 取证方法 |
| --- | --- |
| 最小运行可复现 `minimal_run` | 按项目声明的环境和安装方式，通过使用者拿到的交付物运行最小样例，直到得到有业务意义的输出。记录版本、目录、命令、输入及第一个成功结果或失败位置。区分交付物缺资源和当前机器缺少已声明依赖。 |
| 业务行为符合约定 `business_rule` | 从已认可的规则、契约或验收样例确定预期，选择能区分两种结果的输入，核对实际入口的输出或持久化状态。例如空订单约定只输出表头，逐行检查导出内容。规则冲突时列出双方出处，标为「待确认」。 |
| 回归验证有效 `regression` | 从常用测试命令追到发现规则、实际用例及断言，核对输入是否触发该行为。已有 CI 时检查其工作目录、筛选和跳过条件。说明哪项错误会让断言失败。例如常用命令运行了空订单用例，但它只断言文件存在，可证实缺少表头断言。缺少用例时列出检索过的套件及范围。 |
| 契约兼容 `compatibility` | 这条路径承诺支持旧输入或存在公开契约时，选择一个真实消费者依赖的调用或受支持的历史样例，核对返回内容、默认值或错误行为。记录承诺来源。 |
| 中断与重试 `retry` | 这条路径支持重试或多步写入时，在可丢弃的样例数据上选一个中断点或重复输入。从重试约定、消费机制或多个写入点核实触发依据，再记录第一次的副作用、第二次的结果及预期状态。普通 CLI 可被手动再次运行，本身不足以触发此项。 |

### 按业务约定触发的专项

| 检查项 | 触发依据与实跑方法 | 明确结论所需的专项字段 |
| --- | --- | --- |
| 跨入口业务规则一致性 `cross_entry` | 至少两个入口执行同一条已确认的规则时，用相同数据和初始状态分别运行，比较规则约束的字段或副作用。如列表和导出都须排除已取消订单，分别核对计入的订单。日期或展示格式可有各自的约定。共同口径不明时记「待确认」，有明确例外时写出依据。 | 用一份 `input`、`expected`、`basis` 表达共同样例与约定。`entries` 逐个填写不同的 `entry`、实际 `operation` 和 `observed`，至少两个入口。 |
| 存量数据迁移与恢复 `data_migration` | 表结构、文件格式或状态含义变化时，从受支持旧版的副本走真实升级入口，核对关键值、记录或关联，再演练项目承诺的回退或备份恢复。只支持单向迁移时记录已有约定。 | `before`、`after`、`recovery` 分别记录迁移前、升级后和恢复观察。若升级已失败，写清哪一步尚未到达。 |
| 并发写入一致性 `concurrent_writes` | 不同操作可同时写同一状态时，用可重放的同步点让操作真正重叠，从正常入口核对各请求结果和最终状态。例如两笔订单竞争最后一件库存。 | `overlap` 记录重叠如何得到证实，`outcomes` 记录各操作结果，`final_state` 记录最终业务状态。 |
| 权限与数据隔离 `access_scope` | 入口按身份、角色或租户约束资源时，用既有授权规则和合成身份、数据，分别验证允许和受限的动作。读操作核对可见记录，写操作核对拒绝后的状态。 | `allowed`、`restricted` 写明身份、资源、动作和各自结果，`state` 记录数据可见范围或受限操作后的副作用。 |
| 失败可诊断性 `failure_diagnostics` | CLI、后台任务或依赖调用失败需要维护者处理时，重放一个可控失败，沿用户或维护者实际可见的退出状态、错误提示或日志定位原因。 | `signal` 记录收到的失败信号，`location` 写实际能定位的记录、字段、任务或环节，提示过于笼统时写明定位止于哪里。 |

按项目证据选择适用项。已确认入口不具备相应能力时，点名专项可返回「不适用」及依据。本应验证但缺少旧数据、共同约定、并发环境或受控身份等条件时返回「待确认」，写明已观察到的部分。

可能写文件的操作在仓库外的临时副本中运行，副本须对应正在检查的版本，包括范围内的未提交文件。检查提交差异时使用[本次改动质检](change-check.md)确定的版本。会触及真实外部状态的操作使用可隔离的测试依赖；仅有真实服务可用时记录阻塞。运行项目命令由专家负责，汇总脚本只读取 JSON。

实跑后能定位到已声明前提下的失败，可判「发现问题」并说明影响。缺少环境、权威预期或关键资料时，只将依赖它的判断记为「待确认」。入口和预期输出的通过或失败需要实跑证据。入口因资源缺失提前退出时，记录已观察的运行失败，将尚未生成的业务输出标为「待确认」。测试发现与断言可从源码及配置独立核实，标明「仅静态核对」。测试不足和功能输出错误分别取证。未收到某项记录时，覆盖表保留「未查」或已取得的部分。

## 记录与回传

运行 `python3 -B <Skill目录>/scripts/behavior_verification.py [记录文件] --json`。省略文件则从标准输入读取；省略 `--json` 输出 Markdown。`entry` 使用派发的 `unit`，跨入口时可用「订单页与对账导出的销售额」表达范围。`selection` 说明选择依据，首个章节可按惯例带 `project`。全面检查以「行为验证」作为 `selected.check`。指定单项用表中标识。完整行为验证中发现适用的条件项，将它加入记录，缺少实跑条件也须交代原因。点名单项时按派发清单回传。

`checks` 按标识保存记录。每项含 `status`、`mode`（`run` 或 `static`）、`observed` 和可定位的 `evidence` 数组。已实跑须填 `operation`（版本、环境、目录和操作）及 `input`。结论为「范围内未发现」或「发现问题」时还需给出预期 `expected`、预期出处 `basis` 及对应操作、输入；回归验证另填 `test`（用例或检索范围）。发现问题写 `impact`；「待确认」和「不适用」写 `reason`。一条专项记录例如：

```json
{
  "entry": "订单导出",
  "selection": "本轮维护空订单导出规则",
  "selected": [{"check": "regression", "unit": "订单导出"}],
  "checks": {
    "regression": {
      "status": "发现问题",
      "mode": "static",
      "operation": "核对 Makefile 中 test 目标的发现目录和用例正文",
      "input": "空订单列表",
      "expected": "空订单导出缺少表头时应触发断言失败",
      "basis": "README.md#空订单导出",
      "observed": "用例仅调用 exists()，零字节文件也满足断言",
      "test": "tests/test_export.py::test_empty_orders",
      "evidence": ["Makefile:8", "tests/test_export.py:24"],
      "impact": "删除表头后，现有用例仍会通过"
    }
  }
}
```
