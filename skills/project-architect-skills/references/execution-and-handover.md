# 执行复核与维护导读

## 逐项执行与复核

收到用户对当前治理计划的明确批准后，按本轮获批范围执行。部分获批时，将其余入选事项记为「暂缓」。发现需要新增事项或扩大改动范围时，先交代变化并取得该范围的授权。

1. 按计划顺序一次处理一项。重读目标和调用方，对照计划证据、改前基线与当前工作区。把已解决的事项记为「已解决」。新发现的取舍会改变实现或验收时，按[治理选择题](governance-plan.md#治理选择题)请用户决定，并将选择与对应事项一并复核。证据仍不足时记「待确认」，必要验收无法运行时记「待验证」。记录原因后继续处理独立事项。
2. 在目标仓库外保存本项涉及文件的改前状态，包含改前已存在的编辑。记录原先不存在的路径和移动的源、目标位置。将本项编辑限制在计划范围，复查实际差异，并留下可归属于本项的补丁或改后文件状态。
3. 执行验收并记录操作、预期、观察及出处。改代码同时复核结构目标、主要调用方与可见行为，按同一固定输入或测试对照改前结果。补文档时实际按说明走一遍。补图时核对模块、连线方向、对应源码与项目的导出约定。分别记录改前已有的失败和本次新差异。
4. 发现回归时记录失败样例，撤回本项能安全分离的编辑，并重跑相同的检查确认恢复。恢复文件快照前核对当前文件仍处于本项编辑后的状态。文件移动同时核对源和目标，删除本项新增文件前核对其内容归属。若发现他人的编辑，保留重叠位置，记下路径和回退范围，暂停依赖这些文件的后续写入。验收条件在改动后失效时，按相同原则回退并记录「待验证」。完成本项复核后再开始下一项。

### 局部与跨文件重构

局部改动按可独立验证的步骤执行。例如先提取订单筛选条件，重跑基线，再简化循环。每步比较该步骤影响的输出、异常或副作用，最后从主要调用入口执行计划中的整体验收。

跨文件重复修改先做只读预览。重命名优先使用能解析符号绑定的语言工具；替换重复语法可用项目已有的 AST 工具。检查定义、导入别名、再导出和实际调用者，同时用文本搜索补查配置和注册表里的字符串引用。逐处区分同名的其他符号、对外兼容名和本次目标，将预览的文件与获批范围对照。缺少合适工具时，沿已核实的引用手工修改。

按一个可运行的改动单元一起修改定义与依赖它的调用点，查看实际差异并运行相关测试，再处理下一组。语法匹配后仍要核对语义，例如将回调改为异步等待时，检查原回调的返回值、异常传播和执行顺序。把验证过的调用路径和同口径的改前、改后观察分别填入现有的 `behavior` 和 `structure` 检查。

### Python 结构信号增量对照

本项修改 Python 文件时，将实际改前快照与改后对应文件送入 [python_smell_signals.py](../scripts/python_smell_signals.py) 的 `--compare <改前文件> <改后文件>`，沿用本轮[质检口径](code-smells.md#python-结构信号)。快照保留本项开始前已存在的用户编辑。可以重复传入 `--compare` 逐对比较多个文件。文件移动时传入原路径的快照和新路径的文件。只有确认某一侧原本不存在或已经删除时才用 `-`。

每对文件按函数限定名对照超过阈值的信号。`changes` 标出位置，以及新增、消失、加重、减轻或不同指标方向不一的变化。多段嵌套按组数和区域数，复杂条件按命中表达式数和最大条件项数对照。`ambiguous` 列出同名多处定义，`unread` 标明读不到的版本。复核时结合实际改动核实信号，记录新增或消失的异味及改前改后量值。缺少可靠快照或可读源码时，记录取证限制。增量观察供维护者判断，事项的结论取决于原计划的结构与行为验收。

## 导读与报告交付

从当前工作区重新核对下一次维护用得到的入口、调用方和自查方法。用 [Git 共变线索](git-change-history.md)发现可能漏查的调用方、契约和测试，沿当前实现核实。给出仓库相对路径、符号或章节，以及查证过的调用关系。用实际输入、命令或核对步骤说明改完应该看到什么。若本轮改动涉及这个入口，关联已通过的计划事项。回退后以恢复后的实际入口为准。

### 质检摘要

为每类检查填写一条 `summary`，用 `check` 对应 `plan.coverage.selected` 中的检查项，`detail` 简述发现或核实的结果。将五类专家返回的 `results` 原样放入 `plan.coverage.results`。每个模块的 `status` 说明查了多少，`verdict` 说明查出了什么。

新记录由脚本合并同类模块的判定，可省略 `summary[].status`。任一模块发现问题即为未通过；全部未回传为未查；其余含未查或待确认的模块为待确认；全部不适用时保留不适用。其余适用模块均通过时显示通过。表内附上未查或部分已查的范围。若提供显式状态且与合并结果冲突，脚本报错并停止生成。

旧版回传缺少 `verdict` 时仍可沿用原有的显式摘要。新旧回传混用且旧模块的检查结论无法推导时，保留有依据的显式未通过，否则记待确认。核对旧记录后重新用专家脚本生成，即可恢复各模块的结构化判定。

```json
{
  "summary": [
    {"check": "必要文档", "detail": "使用和验证说明齐全。"},
    {"check": "代码异味", "detail": "export.py 的两处表头定义需统一。"}
  ]
}
```

运行 `governance_report.py --summary`，输入只需 `summary` 和含 `coverage` 的已校验 `plan`，也可复用完整报告记录。摘要模式校验计划和逐项结论，只输出「质检项／是否通过／说明」表格及自动生成的一句话总结，授权前无需编造执行复核或导读。无需修复时明确说明；有未通过项时给出数量，具体问题写在表内；待确认和未查不会被汇总成全部通过。缺少 `summary` 时拒绝生成摘要，不从 Markdown 猜测结论。旧记录仍可生成完整报告，新增 `summary` 会同时出现在完整报告开头；完整报告的复核和导读仍按原规则校验。

需要修复授权时，主 Agent 在摘要后简列拟改事项、范围和验收标准，并给出授权选项；不粘贴整份计划。用户要求细节或完整报告时，再展开相应证据、计划和导读。

### 独立维护导读

只需维护定位时，从目标仓库根目录运行 `python3 -B <本 Skill 目录>/scripts/governance_report.py --guide-only`，传入仅包含 `guide` 和按需填写的 `guide_limit` 的 JSON。输出从「维护导读」开始，在当前会话交付。输入可以来自标准输入或记录文件。

每项用 `task` 写维护任务，`entry` 写一个当前文件的定位，如 `orders/export.py::COLUMNS`，`callers` 写已核实的调用方及影响，`evidence` 列出实际读过的定义与调用位置。`checks` 按顺序给出能重放的操作和预期结果。多行命令作为一个字符串传入，保留换行、缩进和 heredoc 的结束行；脚本会生成可直接复制的代码块。预期结果可另列为一条说明。脚本检查入口文件和可定位的本地引用，符号、调用关系与业务含义由取证者打开源码核对。例如两个页面共享 CSV 导出时，从两页分别下载，核对表头，并用带逗号的客户名检查它仍完整地落在一个字段。

仅部分路径可见时，交付已核实的部分，并在 `guide_limit` 写明缺口。尚无可核实入口时传 `{"guide":[],"guide_limit":"实际已查范围和还需取得的资料"}`。涉及本轮拟改入口时走完整治理报告，用已通过复核的 `target` 关联实际改动。

### 维护导读独立复验

正式移交或用户点名复验时，主 Agent 先准备可交付的导读，再选一项相邻维护任务。交给未参与编写的工程文档专家新上下文或实际接手者，只给目标仓库、导读和任务。复验者独立定位修改入口、追踪受影响的调用方，并实际运行能区分正确与错误行为的检查。需要写入时在临时副本操作。主 Agent 将其观察并入交付。新会话演练记录实际复验者，面向新手的试点指标使用真人观察。

完整报告和 `--guide-only` 都接受可选的顶层 `guide_replay`，每次复验一条选中的导读。用 `guide_task` 精确对应 `guide[].task`，`task` 写相邻维护题，`status` 写「通过」「未通过」或「待确认」。

- 复验者实际尝试后给出 `reviewer`、`independent: true`、`operation`、`observed` 和非空 `evidence`。通过还需 `entry`（当前仓库文件及符号）、`callers`（调用位置及影响）、`expected`（足以识别错误的预期）。例如校验表头就核对列名和顺序。
- 已实证导读缺漏、错误或验证无法识别回归时记「未通过」，在 `reason` 写卡住的步骤，可附已核实的部分。缺少独立上下文、可用导读或运行环境时记「待确认」，提供 `task`、`reason` 及已有证据。
- 最终 `--summary` 在原质检表后的一句话中附复验状态和关键观察或阻塞原因。普通维护定位和授权前的预览可沿用原记录。

### 完整治理报告

没有可执行事项、用户拒绝或本轮只读时，沿已核实的业务路径交付导读。用户拒绝时以 `inspect` 模式记录未执行的建议，`reviews` 传 `[]`。资料不足时，给出已读边界和尚需核对的事实。再次调用时依据当前文件重新取证，排除旧报告和临时取证记录。

用 `python3 -B <本 Skill 目录>/scripts/governance_report.py` 从标准输入读取 UTF-8 JSON，也可传入记录文件。以目标仓库为工作目录。报告合并初次质检、改动前的计划、逐项复核和当前导读。必要时在复核中补充修订后的覆盖结论。

- `audit` 为 Markdown 章节数组，可传质检脚本的完整输出。若本轮所有选定范围均未查且已记录在 `coverage`，可传空数组。`plan` 使用计划脚本 `--json` 同次返回的[校验后记录](governance-plan.md#生成报告章节)，其中保留改前证据和本轮范围。
- `reviews` 按计划顺序覆盖每一项执行事项，使用各项的 `target` 对应。没有执行事项时传 `[]`。每项含 `status`。
  - `通过` 记录 `changes`（实际位置与差异）和 `kind`（`code` 或 `handover`）。`checks` 的每项含 `kind`、`operation`、`expected`、`observed`、`result`，结果为「通过」「发现差异」或「待验证」。代码项同时有通过的 `structure` 与 `behavior`，文档与图件有通过的 `handover`。
  - `发现差异` 记录 `changes`、含失败样例的 `checks` 以及 `rollback`。当前验收中任一 `checks` 结果为「发现差异」时，事项状态也须为「发现差异」。`rollback.status` 为「已回退」「部分回退」或「保留现场」，`rollback.evidence` 写明实际恢复或保留的位置与验证结果。
  - `待确认`、`待验证`、`暂缓`、`已解决` 写明 `reason`，可附核对的 `checks`。已经编辑后才受阻的事项还需 `changes` 和 `rollback`。如有改前失败，可用 `preexisting` 单独记录。
  - `structure_delta` 可附非空字符串数组，写明已核对的 Python 结构变化、文件与函数位置，或增量取证的实际限制。
- `guide` 的每项含 `task`（如「调整导出列名」）、`entry`（当前相对路径与符号）、`callers`（已核实的调用方及影响）、`evidence`（出处数组）和 `checks`（按顺序的自查步骤数组，含预期结果）。涉及本轮改动后的入口时填 `target` 关联已通过的计划项。没有可核实的导读时传 `guide: []` 并用 `guide_limit` 说明范围和缺口。有局部限制时也可附 `guide_limit`。

允许写报告时加 `--write`，成功后脚本返回 `docs/project-architect-report.md`。脚本写入的报告带内容校验标记，可以覆盖仍与生成内容一致的上一份报告。刷新时核对文件系统实际换出的版本。遇到并发人工保存，保留其内容并将候选报告返回标准输出。恢复期间又收到其他编辑时，两份改动分别保留，标准错误给出留存路径。文件系统缺少安全替换能力、已有报告来源不明或写入失败时，同样返回完整报告。用户限定只读或仓库不可写时不加 `--write`。会话仍用同一记录的 `--summary` 输出，只在用户要求全文时展示完整报告；保存成功时另附报告路径。`--summary`、`--guide-only` 与 `--write` 不组合使用。
