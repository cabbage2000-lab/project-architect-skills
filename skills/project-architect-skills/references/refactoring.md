# 专项重构

从用户指定的维护任务定位改动。单文件内先选择可独立验证的提取、移动或重命名；同一规则涉及多个入口时，将必须一起生效的改动列入同一计划项。质量评估、计划和执行分别沿用[代码异味](code-smells.md)、[治理计划](governance-plan.md)和[执行复核](execution-and-handover.md)。

## 定位重构对象

| 报告标识 | 确认证据 | 可选改法 |
| --- | --- | --- |
| `long_parameter_list` | 对照签名和实际调用，找出必须成组传入或容易错位的参数。 | 对已有业务概念引入参数对象，核对默认值和关键字调用。 |
| `large_class` | 结合类规模、状态和调用方，定位可以独立测试的职责。 | 提取类，由原入口委托，核对共享状态与初始化顺序。 |
| `data_clumps` | 在多处签名或数据结构里定位共同出现、遵守相同约束的一组值。 | 封装为值对象，并在边界保持原序列化格式。 |
| `feature_envy` | 某方法反复读取另一对象的数据来完成属于后者的规则。 | 将计算移动到数据所属位置，核对依赖方向。 |
| `inappropriate_intimacy` | 一个类依赖另一个类的内部表示，修改表示会迫使调用方同步改动。 | 通过明确操作封装内部状态。 |
| `shotgun_surgery` | 一次业务规则调整需要同步改动多个位置，结合调用链或历史差异说明漏改后果。 | 集中该规则或其选择入口。 |
| `divergent_change` | 多个相互独立的需求反复修改同一类的不同部分。 | 沿变化原因拆分，验证每项职责可独立修改。 |
| `refused_bequest` | 子类禁用继承操作或只能对部分父类调用生效。对照父类约定与实际替换路径。 | 拆分能力或改用组合；涉及行为修正时明确迁移范围。 |

长方法、重复代码和复杂分支沿用已有检查。提取方法时保留执行顺序及副作用；复杂条件可命名为谓词，嵌套可用守卫语句简化；反复按类型分派时评估多态。清理疑似死代码前核对导出、插件发现、反射和配置入口。移除参数还需核对外部签名和兼容调用。

## 结构化批量修改

先以语义工具查定义和引用，重复的语法结构可用 ast-grep 检索和改写。以下示例针对已确认 `response.status` 为 HTTP 状态的 TypeScript 调用，假设文件已导入项目常量 `HTTP_OK`。在项目根目录用实际文件替换示例路径。第一条输出预览；获批后，若该文件的所有命中均经核实，再运行第二条。文件内有混合语义时逐处编辑或用交互模式选择。[ast-grep 重写说明](https://ast-grep.github.io/guide/rewrite-code.html)

```sh
ast-grep run -l ts -p 'response.status === 200' -r 'response.status === HTTP_OK' src/client.ts
ast-grep run -l ts -p 'response.status === 200' -r 'response.status === HTTP_OK' --update-all src/client.ts
```

同样的数值可能表达不同单位、业务规则或协议状态。提取常量时按含义分组，逐组确定名称和定义位置。符号改名时先解析绑定，再核对导入别名、再导出、构造和动态查找。公开入口有外部使用者时，在计划中写明兼容别名或迁移步骤。使用文本替换时只处理已确认的精确位置。

## 旧语法和 API 迁移

| 变换 | 在预览和验收中核实 |
| --- | --- |
| JS/TS 的 `var` 改为 `let` 或 `const` | 检查重新赋值、声明前读取、块外使用和循环闭包；选择符合原作用域和赋值行为的改法。 |
| 函数声明改箭头函数 | 核对声明提升、动态 `this`、`arguments` 及构造调用。 |
| 短路取值改可选链 | 覆盖 `null`、`undefined` 和其他合法假值，核对表达式求值次数与原返回值。 |
| 回调或 Promise 链改为异步等待 | 保留成功回调逻辑、返回值、拒绝处理与并发顺序，从原入口验证异常路径。 |
| Python 格式化与 `super()` 简化 | 保留格式说明、字面花括号和表达式求值次数；核实零参数 `super()` 所在方法的类与首参数绑定。 |
| Go 错误包装 | 核对错误类型、直接相等判断、错误文本及 `errors.Is/As`。新增上下文本身会改变文本，按可见契约处理。 |
| 替换弃用 API | 按项目支持的版本核对新旧签名、默认值、错误与生命周期；追踪所有调用点，并用成功和失败样例对照。 |

## 分批验收与交付

基线记下与本次目标有关的复杂度、重复规则位置或耦合点，以及实际覆盖目标路径的测试。按一个可回退的变换分批，单批少于 1000 个文件；大任务按模块或依赖关系拆分，各批保持可运行。每步运行受影响测试，每个完整变换后运行项目全量测试和适用的构建、类型检查。受环境限制时记录实际执行范围和待验证项。

在现有报告的 `changes` 中写明改动位置、采用的模式和关键差异；`checks` 对照同口径结构量值、行为样例和测试结果。项目已有覆盖率工具时记录相同范围的改前、改后值。导读说明今后从哪一处扩展或维护。需要提交时按独立变换在任务分支暂存对应差异，形成可单独撤销的提交。使用隔离工作树或改前快照保护原有编辑；发现回归时按[逐项回退](execution-and-handover.md#逐项执行与复核)恢复并重测。
