# 项目治理架构师

## 根据用户意图分派

主 Agent 先结合当前会话判断目标、范围和读写限制。用户回答选择题时，接着处理该题对应的事项。对已展示计划的明确批准、部分批准或拒绝直接转到治理流程第 6 步。

「补文档」「补 ADR」或指定编写手册，走[工程文档专家](agents/engineering-documentation-expert.md)的[补文档流程](references/necessary-documents.md#补文档)。「该补哪些架构图」「帮我补架构图」或点名绘制某个视图，走[软件架构专家](agents/software-architecture-expert.md)的[补架构图流程](references/architecture-diagrams.md#补架构图)。同时请求图文时分别取证，共用同一份图源。专家只读取证和拟稿，主 Agent 按用户选择写入并验证。单独请求推荐或补全时，直接交付清单或选定的产物。体检时，各专家先核对[保密文档的 Git 忽略范围](references/necessary-documents.md#保密文档)，将边界传给涉及同一路径的检查项。

用户只问「从哪里改、影响谁、怎么验」时，主 Agent 沿当前业务入口取证，跨模块调用按需交给[软件架构专家](agents/software-architecture-expert.md)追踪。按[独立维护导读](references/execution-and-handover.md#独立维护导读)用 `governance_report.py --guide-only` 在会话直接交付。问「现有说明够不够」属于文档检查。同时要求诊断或修复时按下表分派，维护定位的结果并入同一份治理报告。

| 用户想核实的问题 | 检查项 | 只读专家定义 |
| --- | --- | --- |
| 接手者能否按现有说明启动、测试或部署？能否查到重大架构决策的理由？项目使用的 Codex、Claude Code 或 WorkBuddy 有项目指引吗？哪些文档可以合并？ | 必要文档 | [工程文档专家](agents/engineering-documentation-expert.md) |
| 图中模块和箭头是否符合实际调用？跨服务数据流需要怎样画？ | 架构图 | [软件架构专家](agents/software-architecture-expert.md) |
| 当前模块调用是否违反项目认可的分层约定？ | 架构漂移 | [软件架构专家](agents/software-architecture-expert.md) |
| 测试或源码应放在哪里？这个文件的位置符合包或构建约定吗？ | 目录结构 | [仓库结构专家](agents/repository-structure-expert.md) |
| 这个方法为何难改？如何简化分支、评估设计模式或完成指定重构？ | 代码异味 | [代码质量专家](agents/code-quality-expert.md) |

按用户要求的结果选择专家。比如「README 里的调用图箭头画反了吗」只派软件架构专家；如果还问「新人能照说明跑通测试吗」，再派工程文档专家。把同一专家负责的问题合并派发，保留每个问题各自的目标路径和限制。显式指定的专家、检查项和排除项优先；作为证据提到的文件或模块无需单独派发。

单独调用本 Skill（如 `/project-architect-skills`）、输入「项目评估」、要求全面体检或给项目打分时，默认选四项，再应用用户给出的限制。只给某个检查项或模块打分时按专项处理。只要求查看分数时以只读方式交付。有具体问题但结合上下文仍无法确定分工时，用[带推荐项的选择题](references/governance-plan.md#治理选择题)区分会改变分工的意图，例如调整导出文件归属或简化导出逻辑。请求超出四位专家职责时，说明可覆盖的部分。

用户指定重构目标时，以该目标进入代码治理流程。SOLID 评估与设计模式选型按[设计判据](references/code-smells.md#solid-原则与设计模式)取证；局部清理、跨文件重命名、常量提取和旧 API 迁移按[专项重构](references/refactoring.md)选择变换及验收方式。

## 治理流程

制定计划或执行复核时，先查当前会话、项目约定、调用方和测试。业务规则、兼容范围或验收目标仍需用户取舍，且答案会改变本轮改动时，由主 Agent 调用宿主的 Ask User Question 能力。每个问题都按[治理选择题](references/governance-plan.md#治理选择题)给出可直接选择的方案和一项有依据的推荐。

1. 主 Agent 按[项目规模与取证范围](references/project-size.md)盘点仓库，派发前以「具体检查项、模块或入口」列出必答清单并保留为 `coverage.selected`。全面体检按四项基础检查派发。专项检查沿用判据标识，例如订单与退款的 `architecture_drift` 各占一项。按选中的专家派发独立上下文的只读子 Agent，多项可并行，并发槽位不足时分批派发。
2. 派发时给出目标仓库、维护任务、允许检查的范围、重点入口、对应专家定义的可读取路径及 Skill 根目录，无需传递完整会话历史。让子 Agent 先读该定义，再沿其中的链接取证。宿主通过提示词传递角色时，提供同一份定义的正文和解析链接所需的目录。单项涉及大量模块时，按模块或业务路径分批取证。子 Agent 在自己的上下文内取证并生成章节，按下方[体检分工与回传](#体检分工与回传)交付。
3. 主 Agent 将实际回传与派发清单逐项对照，注明部分已查、未查的范围及原因，按上表顺序合并章节，仅在首个章节记录项目规模。按同一改动目标归并候选并保留各自出处；同一图件缺口归入架构图，同一函数的各类异味合为一项。结论冲突时只复查争议出处，仍无法判定的结论标为「待确认」。子任务中断时，缩小到未完成的模块或入口重新派发，保留已核实结果及剩余未查范围。
4. 在体检后按[治理计划判据](references/governance-plan.md)汇总候选并排序。对相关源码和测试按 [Git 变更证据](references/git-change-history.md)只读取证，供候选排序和导读核对使用。对可能改变既有行为的建议先查调用方、契约或测试中的反例。在目标仓库根目录用 [governance_plan.py](scripts/governance_plan.py) 核对拟执行项的本地出处并生成计划。默认命令用 `execute` 列出评估后最值得本轮优化的事项，数量由评估结果决定。逐项说明推荐理由、改动范围、基线、验收和回退办法。仅检查、用户限定只读或仓库不可写时用 `inspect`。体检、基线取证和计划预览保持目标仓库只读。Python 不可用时按同一判据生成计划。
5. 计划有可执行事项且尚未获得对应授权时，在当前会话给出体检摘要和目标仓库，展示计划脚本 `--preview --json` 返回的 `markdown` 中的计划正文，保留同次返回的 `plan` 供授权和最终报告复用。按[治理选择题](references/governance-plan.md#治理选择题)呈现预览末尾的授权选项，等待用户明确答复。等待期间保持目标仓库只读。用户已明确授权计划中的具体修复时，沿用该授权。只读检查或无可执行事项时，直接进入导读。
6. 用户选择或回复「同意治理」，或以其他方式明确批准具体事项后，沿用本轮计划继续。用户选「逐项选择」时，按计划事项给出执行或暂缓的选择题，已有明确答复的事项沿用原决定。只处理获批的事项，按[执行复核](references/execution-and-handover.md#逐项执行与复核)重查现状、保留改前状态、逐项修复并验收。已解决的事项直接跳过，拟变更超出获批范围时先展示新范围并等待确认。部分批准时，其余已列事项记为「暂缓」，不递补。用户选择仅交付检查结果或拒绝治理时按 `inspect` 交付，注明拟修复事项未获批准。收到「同意治理」时若没有可核对的待授权计划，先重新取证并展示计划。
7. 按[维护导读与交付](references/execution-and-handover.md#导读与报告交付)重读当前入口及调用方，给出下次维护的自查步骤。用 [governance_report.py](scripts/governance_report.py) 汇总体检、计划、复核和导读。再次启动治理时从当前仓库重新判断规模并取证。

治理获批或用户明确要求保存报告且仓库可写时，用 `--write` 交付到 `docs/project-architect-report.md`。其余情况以及脚本返回报告正文时，将完整 Markdown 正文原样放入最终回复。环境无法运行 Python 时，按判据汇总报告并沿用同样的交付和覆盖条件。

## 体检分工与回传

专家按定义引用的判据核实适用性、已查范围、维护影响和未读资料。用 `python3 -B` 通过标准输入把检查记录交给对应脚本；仅排在首位的检查项传入主 Agent 提供的 `project`。脚本路径相对于本 Skill，证据路径相对于目标仓库。Python 不可用时按同一判据整理章节。

四类检查均把同一入口的派发清单作为 `selected` 交给脚本，用 `--json` 回传章节、`results` 和 `assessments`。主 Agent 以原清单核对覆盖，将确认发现按根因归并并填入计划的 `scoring`。每轮在目标仓库运行计划脚本 `--json`，待授权时加 `--preview`。复用返回的 `plan` 在最终报告展示体检基线。漏回项显示「未查」，受影响的分项显示「待补查」。治理后按原范围重新取证，将 `reassessment` 随最终报告交付。[评分规则与复评记录](references/health-score.md) · [专项记录与覆盖](references/governance-plan.md#检查范围记录)

子 Agent 按派发的检查项和模块或入口回传核对情况、可合并的 Markdown 章节及治理候选。候选写清目标、影响和可定位的出处，原始源码、扫描日志和取证对话留在各自上下文。章节过长且有共享临时目录时，可将章节存到目标仓库外的本轮临时文件，回传路径、已查与未查范围及候选，供主 Agent 组装完整报告。交回结果即结束本次分工，后续计划、授权与报告由主 Agent 统一处理。宿主无法派发子 Agent 时，由主 Agent 读取选中的专家定义，逐项完成并汇总，交付时说明实际检查方式。
